# UI/UX 無障礙設計規範

> 適用對象：設計師、前端工程師、PR Reviewer
> 適用範圍：`oingg-web-nuxt` 所有頁面與元件（Nuxt 4 + Vue 3 + Element Plus，深色主題，行動優先的響應式網頁）
> 目標等級：**WCAG 2.2 AA**（同時對照台灣現行「網站無障礙規範」與 NCC「行動版應用程式(APP)無障礙開發指引」中適用於行動版網頁的項目）

無障礙不是上線後補的檢查表，是每個畫面設計稿與每個 PR 都要過的門檻。這份文件把抽象的規範，翻譯成這個 codebase 裡看得到、抄得到的具體做法。

## 1. 四大原則對照（WCAG POUR）與本專案做法

### 1.1 可感知 Perceivable

| 規範 | 標準 | 本專案做法 |
|---|---|---|
| 文字替代 | 1.1.1 (A) | 所有 `<img>`、`el-icon` 純裝飾用途加 `aria-hidden="true"`；有意義的圖片（如公司 logo、圖表縮圖）需有 `alt`。純裝飾圖不需 `alt` 說明。 |
| **色彩不可為唯一辨識依據** | 1.4.1 (A) | **目前風險點**：`StockScreenerResultTable.vue` 等元件用 `--el-color-danger`（紅）/`--el-color-success`（綠）純色表示漲跌，沒有第二種視覺線索。**必須**加上 `▲`/`▼` 符號、`+`/`-` 前綴，或粗細差異，色弱使用者才能分辨漲跌方向。ECharts 圖表（`CHART_DIVERGING`、`CHART_RIVER_LINES`）同理，用 tooltip 文字或圖案輔助。 |
| 對比度（文字） | 1.4.3 (AA) | 一般文字 ≥ **4.5:1**；大字（≥24px 或 ≥18.66px 粗體）≥ **3:1**。深色主題（`#000000` 頁面底 / `#121212` 卡片底）務必用工具或公式實測，不能只憑肉眼——灰階文字最容易落在門檻邊緣，實測方法見第 5 節。 |
| 對比度（UI 元件與圖形） | 1.4.11 (AA) | 按鈕外框、表單邊框、圖示、圖表資料點等「非文字」元素，與相鄰背景對比 ≥ **3:1**。深色主題下要特別檢查 `disabled` 狀態、表格分隔線（`gridline: #2a2a2a` 對 `#121212` 背景過近，僅適合裝飾性格線，不可承載語意）。 |
| 文字可縮放 | 1.4.4 (AA) | 瀏覽器縮放至 200% 不得造成內容遺失或功能失效。**已修正**：本專案原本完全沒有 `<meta name="viewport">`（Nuxt 不會自動注入），手機上會用桌面版寬度渲染整頁，等於連響應式設計都沒生效，遑論縮放測試。已於 `nuxt.config.ts` 補上 `width=device-width, initial-scale=1`——**刻意不加 `maximum-scale`/`user-scalable=no`**，因為那兩個參數會直接鎖死縮放，是 1.4.4 最常見的違規寫法。另外避免用固定 `px` 高度包住文字容器；`StockScreenerResultTable` 欄位寬度盡量用 `min-width` + 彈性排版而非寫死高度。 |
| 文字間距可調整 | 1.4.12 (AA) | 常被誤解成「預設樣式要長這樣」，實際規範是：**當使用者自行套用**行高 ≥ 字級 1.5 倍、段落間距 ≥ 字級 2 倍、字距 ≥ 字級 0.12 倍、字間距 ≥ 字級 0.16 倍（例如瀏覽器套件強制套用）時，畫面不可裁切、重疊或喪失功能，不是要求開發者預設值必須精準等於這些數字。已於 `main.css` 的 `html, body` 補上 `line-height: 1.5` 作為安全基準（只影響沒有自訂 line-height 的一般文字，不影響 Element Plus 元件自己的密度設定）；新增內文/段落樣式時避免用固定小行高（如 `line-height: 1` 或 `1.1`）鎖死。 |
| 版面重排 | 1.4.10 (AA) | WCAG 的最低合規門檻是視窗寬度縮至 **320px**（相當於 1280px 版面縮放到 400%）不應出現雙向捲軸、不失去功能——這是靠瀏覽器縮放才會遇到的情境。**本專案的產品基準線更嚴格：實體手機最小寬度 360px 必須完全不跑版**（不只是「功能還在」，是要正常好看），詳見下方「最小支援寬度」說明。資料表格（screener 結果表）屬公認例外，允許表格內部水平捲動，但捲動容器需可用鍵盤操作（`tabindex="0"` + `role="region"` + `aria-label`）。 |
| 非純音訊/視訊內容 | 1.2.x (A/AA) | 目前專案無影音內容；未來若加入教學影片、圖表動畫解說，需提供字幕或文字說明。 |
| 內容自動更新的通知 | 4.1.3 (AA, Status Messages) | 篩選結果更新、即時報價變動等不需搶焦點但需通知的內容，用 `aria-live="polite"` 包住結果區塊，讓螢幕報讀器感知資料已更新，不用強制搬移鍵盤焦點。 |

> **關於「16px 預設字級」「用 em/rem」**：這兩點是業界公認的最佳實踐（讓文字能跟著使用者的瀏覽器/OS 縮放設定走），**不是** WCAG 條文本身要求的數字——WCAG 對「應該用哪個 CSS 單位」或「預設字級必須是幾 px」沒有硬性規定，真正可測試的成功準則是上面表格的 1.4.4（能縮放到 200%）跟 1.4.10（320px 寬度不崩版）。但**本專案自訂了比 WCAG 底線更嚴格的產品基準**（跟第 1.1.1 節 360px 最小寬度是同一種「WCAG 沒強制，但我們自己要求」的規則）：**16px 是全站唯一字級下限，沒有例外**。Element Plus 元件（按鈕、輸入框、表格儲存格）預設的 `--el-font-size-base: 14px` **不再被視為資料密集介面的合理例外**——2026-08-31 起這條例外已經取消，一律要求 16px 起跳。實作方式：`main.css` 的 `:root` 直接覆寫 `--el-font-size-base: 16px`，這個變數是 Element Plus 內部絕大多數元件（表格、按鈕、輸入框、下拉選單…）預設字級的共同來源，改這一個變數就能全域生效，不需要每個元件各自加 `:deep()` 覆寫（`size="small"` 變體是唯一例外，它的 12px 是寫死的字面值、不是走這個變數，仍需要 `.el-input--small` 那條個別規則）。新元件如果要用相對單位，優先用 `rem`（相對根字級，不受父層 `em` 疊乘影響），而非硬性要求把既有 `px` 值全部回頭改掉。

### 1.1.1 最小支援寬度：360px（本專案產品基準，比 WCAG 底線更嚴格）

**規則：任何頁面在 360px 寬度的手機上都不能出現版面跑掉（元素被裁切、重疊、把整頁往右推出視窗），這是設計稿與 PR 都要過的硬門檻，不是「有空再修」的優化項。**

**為什麼是 360px，不是 320px**：320px 是 WCAG 1.4.10 的合規底線，但那主要對應「桌機頁面縮放到 400%」這種情境，現今已經找不到真的只有 320px 寬的手機在賣。**360px（CSS px）才是目前市面上最小的主流 Android 機種實際寬度**（例如多代 Galaxy S/Pixel 入門機型），iPhone 最小的 SE 系列也有 375px。所以本專案把 360px 訂為「必須完全不跑版」的產品基準線，320px 仍要維持 WCAG 要求的「不失去功能」（可以擠、可以捲，但不能整個壞掉），兩者是不同嚴格程度的兩條線，不要混為一談。

**目前程式碼掃描結果**（作為之後改動的參考基準，非窮舉，新元件仍要自行複查）：
- ✅ `StockFilterSlotCard.vue` 的數字輸入區用 `flex: 1; min-width: 0`，會隨容器收縮，360px 下不會撐開卡片。
- ✅ `StockScreenerResultTable.vue`／`StockTable.vue` 的欄位寬度（`width="100"` 等）在窄螢幕下會讓 `el-table` 自動內部水平捲動，屬 1.4.10 認可的資料表例外，捲動只發生在表格內部，不會把整個頁面撐寬。
- ✅ `el-popover` 寬度（`width="200"`／`"220"`／`"240"`）都小於 360px 扣除左右內距後的可用寬度，不會超出視窗。
- ⚠️ 沒有在真機或 360px viewport 下實際跑過登入後的畫面（screener 篩選網格、watchlist 表格/卡片切換）——這類需要登入資料的頁面目前只能用靜態掃描推論，**合併前務必用 DevTools 裝置模擬手動看過一次**，尤其是欄位多、文字長的表格列與 `StockCard`。

**設計/開發實務作法**：
- Flex/Grid 子項預設補上 `min-width: 0`（或 `overflow-wrap: anywhere` 給長字串如公司名稱、代號），避免內容把 flex 容器撐爆——這是 360px 跑版最常見的成因，比「元素本身太寬」更常見。
- 避免任何跨頁面共用元件寫死 `width` 超過 320px（優先用 `min-width`/`max-width`/`flex-basis`），表格/圖表這類必然較寬的內容則刻意讓它在自己的容器內捲動，不要讓 `overflow` 逸出到 `body`。
- 設計稿至少要出 360px 寬的版本給工程師對照（不是只出手機稿「示意」，寬度要精確標註），有堆疊、換行、截斷疑慮的區塊要特別註明預期行為。

### 1.1.2 標題字級與階層（h1～h6）

WCAG 對標題字級沒有具體數字要求，只要求標題的**語意結構**要正確（1.3.1）、順序不可跳級（2.4.6 建議）。字級大小是排版慣例，不是硬性條文——但既然要定調，就跟著本專案既有的視覺語言走，而不是照搬行銷/編輯型網站的通用範例（那種 40px+ 的 h1 放到這種資訊密集的股票篩選工具會顯得突兀）。

**現況**：`index.vue`、`screener.vue`、`watchlist.vue`、`operation-stats/index.vue` 四個頁面的 `<h1>` 已經一致寫死 `font-size: 20px; font-weight: 600;`，且**目前整個專案完全沒有用到 `<h2>`～`<h6>`**——每個路由就是一個 h1 頁面標題，下面直接接 tabs/表格，標題階層是扁的。

**本專案字級規範**（以既有 20px h1 為頂點，向下疊一組緊湊比例，而非從 16px 往上疊出編輯型網站那種大 h1）：

| 標籤 | rem | px | 用途 |
|---|---|---|---|
| h1 | 1.25rem | **20px**（維持現況） | 頁面標題（每個路由一個） |
| h2 | 1.125rem | 18px | 頁面內主要分區（例如 screener 的「篩選條件」「搜尋結果」） |
| h3 | 1rem | 16px | 次分區標題 |
| h4–h6 | 1rem | 16px，改用 `font-weight`（如 600）、顏色（`--el-text-color-secondary`）或字距/大寫區分層級 | 更細的分組標籤 |

**h4 以下刻意不再往下縮小於 16px**——呼應第 1.1 節「16px 是內文可讀性底線」的說明。標題比內文還小既不好讀，視覺上也違反直覺（看起來像排版錯誤，不像更低層級的標題）。層級不夠時改用粗細/顏色/間距去區分，不要繼續往下砍字級。

**待補（不是這次的範圍，先記錄）**：目前扁平的標題階層在頁面內容變複雜時會讓螢幕報讀器使用者難以用「依標題導覽」快速跳轉（例如 screener 頁面的篩選區塊、搜尋結果區塊目前都沒有語意標題）。之後若頁面內容變複雜，應該考慮在頁面內主要分區補上 `<h2>`，而不是只靠視覺分隔（卡片邊框、間距）表達分區。

### 1.2 可操作 Operable

| 規範 | 標準 | 本專案做法 |
|---|---|---|
| **觸控目標尺寸** | 2.5.8 (AA, WCAG 2.2) | 可點擊元素熱區 ≥ **24×24 CSS px**（不足時需與鄰近目標間距補足，或有替代大目標）。本專案是行動優先介面，**建議直接比照 NCC 行動指引採用 44×44px（iOS HIG）/ 48×48dp（Material）作為主要操作按鈕的目標**，尤其 `AppMenuBar`、`AppFeatureMenu`、篩選器的圖示按鈕（icon-only button）。 |
| 鍵盤可操作 | 2.1.1 (A) | 所有互動元素必須能用 `Tab`/`Enter`/`Space`/方向鍵操作，不可只綁 `@click`。自訂拖曳排序（`StockScreenerResultTable` 用 `sortablejs`）**必須**提供鍵盤替代方案（例如「上移/下移」按鈕），否則螢幕報讀器與鍵盤使用者無法調整欄位順序。 |
| 無鍵盤陷阱 | 2.1.2 (A) | `el-dialog`、`el-drawer`、下拉選單開啟時，焦點需困在對話框內（Element Plus 元件預設有做，但自訂 Popover/Menu 要驗證），並可用 `Esc` 關閉、關閉後焦點還原到觸發元素。 |
| 焦點可見 | 2.4.7 (AA) / 2.4.11 (AA, WCAG 2.2 焦點不被遮蔽) | 不可用 `outline: none` 移除瀏覽器預設焦點框卻不提供替代樣式。深色主題要確保 focus ring 顏色（建議沿用 `--el-color-primary` 金色）在黑底上仍清楚可辨，且 sticky header（`AppMenuBar`）或 `AppPinnedSidebar` 不能把 focus 中的元素完全遮住。 |
| 手勢操作有替代方案 | 2.5.1 (A) | `sortablejs` 拖曳排序、圖表縮放/平移等多點觸控手勢，需提供單點觸控或按鈕的替代操作路徑。 |
| 跳過重複區塊 | 2.4.1 (A) | 頁面最上方提供「跳到主內容」連結（skip link），略過 `AppMenuBar`/`AppPinnedSidebar` 重複導覽。`default.vue` layout 中補上。 |
| 頁面標題 | 2.4.2 (A) | 每個 route 用 `useHead({ title })` 設定具描述性標題（例如「個股篩選器 - Oingg」），而非全站共用同一標題。 |
| 動畫閃爍 | 2.3.1 (A) | 任何 1 秒內閃爍 ≥3 次的動畫效果一律禁止（含股價跳動特效、載入動畫）。 |
| 充足時間 | 2.2.1 (A) | 若未來加入登入 session 逾時，需提供延長時間的機制與到期前提醒。目前專案（Firebase Auth）由 SDK 處理，需確認 token 過期不會無預警把使用者踢出正在編輯的畫面（如自訂 preset 尚未儲存）。 |

### 5.1 對比度怎麼實測（WCAG relative luminance）

深色主題最容易出問題的不是「背景太黑」，而是文字顏色被調得太灰太暗、跟背景亮度差距不夠。**背景越黑，其實越容易讓亮色文字過關**——WCAG 對比度公式是：

```
對比度 = (L_亮 + 0.05) / (L_暗 + 0.05)
```

`L`（relative luminance）由 sRGB 每個色版線性化後加權而來（權重 R 0.2126 / G 0.7152 / B 0.0722）。背景的 `L_暗` 越接近 0（純黑 `#000000` 的 `L = 0` 是理論最小值），分母就越小，同一個文字亮度算出來的比值就越高。所以問題永遠出在「前景色不夠亮」，而不是「背景太黑」。

**日常操作**：不用手算，貼進 [WebAIM Contrast Checker](https://webaim.org/resources/contrastchecker/) 或用 Chrome DevTools 點文字色票即可。需要批次驗證色票（例如一次檢查整份色盤）時，可以用下面幾行 Node 直接算：

```js
function luminance(hex) {
  const c = hex.match(/\w\w/g).map(x => parseInt(x, 16) / 255)
    .map(v => (v <= 0.03928 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4))
  return 0.2126 * c[0] + 0.7152 * c[1] + 0.0722 * c[2]
}
function contrastRatio(fg, bg) {
  const [hi, lo] = [luminance(fg), luminance(bg)].sort((a, b) => b - a)
  return (hi + 0.05) / (lo + 0.05)
}
```

**本專案實測案例**（作為之後檢查新色票的參考基準）：

| 前景 | 背景 | 對比度 | 4.5:1（一般文字） | 3:1（大字/UI元件） |
|---|---|---|---|---|
| `--el-text-color-secondary` `#a3a6ad` | `--el-bg-color` `#121212` | 7.69:1 | ✅ | ✅ |
| `CHART_INK.secondary` `#b3b3b3` | `#121212` | 8.93:1 | ✅ | ✅ |
| `CHART_INK.muted`（**修正前** `#7a7a7a`） | `#121212` | 4.36:1 | ❌ | ✅ |
| `CHART_INK.muted`（**修正後** `#808080`） | `#121212` | 4.74:1 | ✅ | ✅ |

`CHART_INK.muted` 用在圖表座標軸標籤（`axisLabel`，字級 11px，遠低於「大字」門檻），必須符合 4.5:1；已於 `app/utils/chart-palette.ts` 從 `#7a7a7a` 調整為 `#808080` 修正（詳見第 6 節）。新增任何灰階文字色票時，套用同一套公式或流程重新驗證，不要只靠肉眼判斷「看起來夠亮」。

## 7. 色彩與排版系統（源自高齡/近退休金融科技暗黑模式設計研究）

本節整理自專案內兩份設計研究文件：`docs/Dark-Mode Homepage Design Guide .md`（英文，通用暗黑模式金融首頁研究）與 `docs/Senior Fintech Dark Mode Design.pdf`（中文，聚焦近退休/高齡投資人）。兩份都是**研究參考文件，不是本專案已核定的規範**——內容有參考價值，但每一項是否採用都個別評估，不是照單全收。

### 7.1 品牌色：維持金黃色，不採用文件建議的藍色

兩份文件都把「品牌/互動強調色」建議為藍色（英文版 Primer 藍 `#2F81F7`/`#58A6FF`；中文版 Sky 400 `#38BDF8`），理由是藍色對高齡族群讀起來較穩重可信賴。**本專案決定不採用**，`--el-color-primary: #d4a72c`（金黃色）維持不變。理由：
- `main.css` 已有明確註解說明金色是刻意選的品牌色，且刻意跟紅漲綠跌的語意色分開，不會混淆。
- 金色在台股/理財語境有既有的文化聯想（財富、金融），比通用建議的藍色更貼合這個產品的定位。
- 文件的藍色建議是「泛用最佳實踐」，不是這個產品的專屬研究結論，不足以推翻既有、有意識做出的品牌決策。

以下各節談的是**主色以外**、跟藍/金選擇無關的具體建議，逐項標註「本專案現況」與「是否採用」。

### 7.2 表面明度階梯（Surface Elevation）——**已決定：捨棄純黑，改用近黑三階**

文件建議用「明度階梯」取代陰影表達層次：base → L1（卡片）→ L2（浮層/選單），例如 `#121212 → #1E1E1E → #2A2A2A`。

**舊狀態**：`main.css` 原本是 `--el-bg-color-page: #000000` 頁面、`--el-bg-color: #121212` 卡片、`--el-bg-color-overlay: #1a1a1a` 浮層——概念上已經是階梯式設計（三層依序變亮，方向正確），只是**頁面用了純黑 `#000000`**。兩份文件都獨立點名這個組合（純黑背景 + 近白文字）容易誘發「光暈效應」（halation）：邊緣擴散、筆畫沾黏，對散光使用者（文件引用的研究估計約 30–50% 人口有不同程度散光）與老花眼使用者疊加後更明顯。

**決定：採用**，已修改 `main.css`：

| Token | 舊值 | 新值 |
|---|---|---|
| `--el-bg-color-page`（頁面） | `#000000` | `#121212` |
| `--el-bg-color`（卡片） | `#121212` | `#1e1e1e` |
| `--el-bg-color-overlay`（浮層） | `#1a1a1a` | `#2a2a2a` |

三層整體「往上平移一階」，不是隨便調亮——`#121212` 正是 Material Design 官方深色主題建議的基底色（兩份文件都引用這個數值），沿用它當頁面底色，讓卡片/浮層繼續在它上面疊加，比起發明新的近黑值更有依據。

**決定依據（實測，避免只憑感覺調色）**：

| 前景 | 背景 | 對比度 | 說明 |
|---|---|---|---|
| `--el-text-color-primary` `#e5eaf3` | 舊頁面 `#000000` | 17.39:1 | 舊狀態：遠超 AAA，這正是被文件點名的「過度反差」 |
| `--el-text-color-primary` `#e5eaf3` | 新頁面 `#121212` | 15.52:1 | 新狀態：反差降低，但仍遠超 AAA（7:1）門檻，不犧牲可讀性 |
| `--el-color-primary`（品牌金） `#d4a72c` | 新頁面 `#121212` | 8.35:1 | 金色主色不受影響，AAA 等級 |

**連帶修正**：卡片色從 `#121212` 變亮到 `#1e1e1e` 後，`app/utils/chart-palette.ts` 的 `CHART_INK.muted`（第 5.1/6 節才剛修過的圖表座標軸文字色）因為背景變亮而**重新跌破 4.5:1**（`#808080` 對新卡片色只剩 4.22:1）——背景變亮會讓固定的中灰前景色對比度下降，跟背景變暗時相反。已再次調整為 `#888888`（對 `#1e1e1e` 為 4.70:1）。這是一個好例子說明：**任何時候調整 surface 色票，都要重新跑一次第 5.1 節的實測，不能只驗證改動當下的那一組配色。**

其餘既有色票（`--el-text-color-secondary` 對新卡片 6.84:1、對新頁面 7.69:1；`CHART_INK.secondary` 對新卡片 7.95:1）都仍穩固過關，無需調整。

### 7.3 文字色階

**本專案現況**（Element Plus 深色主題預設，未覆寫）：`--el-text-color-primary #e5eaf3`、`--el-text-color-secondary #a3a6ad`（對 `#121212` 為 7.69:1，已在第 5.1 節驗證過）、`--el-text-color-placeholder #8d9095`、`--el-text-color-disabled #6c6e72`。

文件建議的 Slate 色階（`#F1F5F9`/`#CBD5E1`/`#94A3B8`）在精神上跟現況接近（都是冷色調、非純白的漸層灰階），現況已經達 AA 甚至多數達 AAA（見 5.1 節實測表）。**不需要跟進調整**，現有色階已經足夠；若未來想更進一步把常規文字對比推到 AAA（7:1）以上，可以參考文件數值，但目前 AA 已是穩固基礎。

### 7.4 漲跌色：降飽和 + 三重編碼

文件建議漲跌色降飽和（如薄荷綠 `#34D399`/珊瑚紅 `#F87171`，取代高飽和螢光色），理由是飽和度 >80% 的顏色在深色背景上會有「色差立體效應」（Chromostereopsis，紅綠等不同波長對焦時前後錯位、視覺跳動）。**本專案現況**：`--el-color-danger: #e0332a`（自訂，較飽和的紅）、成功色沿用 Element Plus 預設 `#67c23a`，都比文件建議的降飽和版本更鮮豔。

**這跟第 6 節第 1 點已經記錄的風險是同一件事，但文件補了一個新角度**：不是只有「純色編碼」違反 1.4.1 這個問題，飽和度本身也可能造成視覺疲勞/立體錯位的次要問題。三重編碼（顏色 + ▲/▼ 符號 + 正負號）仍然是**必須做**的部分，跟選什麼色階無關；降飽和則是錦上添花的選項，可以之後再評估，不影響是否合規。

### 7.5 觸控熱區：48px vs 44px

文件建議統一 48×48px（含高齡使用者手指微顫的容錯）。**本專案現況**（第 1.2 節）已經定為 44×44px（iOS HIG）/48×48dp（Material）並用於主要操作按鈕，方向一致，數字上文件更嚴格一點。**現有 44px 門檻維持不變**——48px 是可以之後再收緊的選項，不是現在就要改的東西。

### 7.6 字級：18px body vs 16px 底線

文件是「近退休/高齡受眾專屬」研究，建議內文基準抬高到 18px（不只是我們現有 16px 底線），標準字重內文級距也拉大到 15–16px 起跳。**本專案現況**：第 1.1 節已定 16px 為不可退讓的底線，且（2026-08-31 起）Element Plus 元件預設 14px 的例外已經取消——`--el-font-size-base` 全域覆寫為 16px，表格/按鈕/輸入框不再有 14px 的空間。

**不建議直接跟進 18px**：這個產品的受眾是「所有想篩選股票的人」，不是文件鎖定的高齡族群專屬產品；貿然把全站基準字級拉到 18px 會讓已經很滿的 screener 表格更擠，牽動大量既有版面。18px 維持在「未來若確認產品要往高齡/穩健理財受眾定位靠攏，可以考慮的升級選項」，不現在做。

### 7.7 版面寬度——**已決定：維持滿版 RWD，不設容器上限**

文件建議容器最大寬度限制在 1280–1440px（理由：超寬螢幕會讓眼球過度橫向掃視，尤其對長者不友善）。這跟本專案稍早才做的決定直接衝突——`screener.vue`/`watchlist.vue`/`operation-stats/index.vue` 才剛把原本的 `max-width: 1080px` 拿掉，改成滿版撐滿可用寬度（見第 8 節變更紀錄）。

**決定：維持滿版，不採用文件的容器上限建議**。理由：

1. **這是本專案明確、剛做出的產品決策，不是慣例沿用**——拿掉 1080px 上限是特意要求的改動，不是舊碼遺留，沒有新證據不應該回頭推翻剛做的決定。
2. **文件的論點是為「長篇閱讀」場景設計的，這個產品的頁面是「資料查找」場景**：文件援引的「超寬螢幕眼球橫向掃視疲勞」研究，前提是使用者在讀連續的文字內容（段落、文章），視線需要頻繁換行橫掃。screener/watchlist 這類頁面是表格/篩選卡片，使用者是「查數據」不是「讀文章」——寬螢幕上能一次看到更多欄位、更多股票，是資料密集工具的可用性優勢，不是文件描述的那種負擔。
3. **文件本身鎖定的受眾（近退休/高齡投資人）跟本專案定位不同**：本專案是「所有想篩選股票的人」都能用的通用工具，不是文件研究的高齡專屬產品，不需要照搬對方受眾優化出來的版面決策。

**但保留文件論點裡跟寬度無關、確實通用的部分**：如果這個產品未來加入長篇的文字內容（例如個股分析說明、教學文章），那些**文字區塊本身**應該用 `max-width`（約 65–75 字元寬，對應排版慣例的可讀行長）個別限制，而不是把整個頁面容器夾窄——寬度限制要下放到「真的在長篇閱讀的那個元素」，不要為了保護少數文字區塊犧牲整個資料頁面的密度。目前專案內沒有這類長文內容，此規則先記錄，供未來新增內容頁面時參考。

### 7.8 間距、字距、行高等其餘建議

文件的 8pt 間距刻度（8/16/24/32/48/64）、行高 ≥1.5×、字距 ≥0.12×、段落間距 ≥2× 字級，跟第 1.1.2 節、第 1.1 節已經記錄的規則一致（後者直接對應 WCAG 1.4.12），**沒有新增或衝突的部分，不需要額外處理**。
